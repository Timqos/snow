# Snow: аудит вихідного Skiff

Базова прошивка зібрана у хмарному Linux x86-64 без змін синтезу.
JieLi toolchain: `20260730.1`; SDK: `AC79NN_SDK_V1.2.1_2023-12-13`.
Компілятор і три SDK-файли мають фіксовані SHA-256 у скриптах cloud-збірки.

## Що вже є

- `firmware/src/core.h`: 6 доріжок, 64 кроки, бюджет 8 одночасних голосів;
  12 лише за умови активного й працездатного другого ядра.
- `seq.c`, `motion.c`, `bank.c`: секвенсор, покрокові параметри й банк патернів.
- `mod.c`, `voice.c`: наявна модуляція та два LFO; їхнє використання треба
  прив'язати до майбутніх параметрів шести спеціалізованих інструментів.
- `eng_fm6.c`, `drumx_voice.c`: корисні відкриті FM-компоненти, але це ще
  не наші шість постійних машин KICK/SNARE/HAT/PERC/BASS/CHORD.
- `fx.c`: окремий insert доріжки та спільні шини chorus/delay/reverb.
  Поточні sends не виконують вимогу незалежних повних ланцюгів FX.
- `web/emu/`: той самий C-код, зібраний у WebAssembly; екран, клавіші,
  MIDI, ручки, transport і збереження перевіряються в Node.js.

## Виміряна місткість базової збірки

Це результати linker/build-перевірок, не вимірювання часу на фізичному FM-1.

| Область | Зайнято, байт | Межа, байт | Залишок, байт |
| --- | ---: | ---: | ---: |
| Образ застосунку | 566984 | 581564 | 14580 |
| RAM data + bss | 83944 | 98304 | 14360 |
| RAM pool | 347300 | 356352 | 9052 |
| RAM code + ramx | 24240 | 24576 | 336 |

Пакет `.fwsc`: 610429 байт, власний update loader: 7273 байти.

## Початкові бюджети для реалізації

- Починати з одного ядра та **8 голосів загалом**: 5 одноголосних
  інструментів + 3 голоси CHORD. Це розподіл голосів, не гарантія допустимого CPU.
- Аудіоблок: 128 frames при 44,1 кГц, приблизно 2,9 мс. Початкова ціль
  проєктування — вкладатися у 2,0 мс найважчого блоку на реальному пристрої,
  залишаючи запас на вводи/виводи; перевіряти піки й underruns.
- Перед новими DSP-алгоритмами прибрати непотрібні движки й семплерні
  ресурси з кінцевої Snow-збірки: запас RAM-коду зараз лише 336 байтів.
- Кожен новий інструмент і FX супроводжувати різницею секцій через
  `tools/size_diff.py`; не перевищувати жодної межі linker-а.
- Незалежні delay/reverb потребують окремого розподілу пам'яті. Наприклад,
  шість моно delay по 250 мс, 16 біт, 44,1 кГц — приблизно 132300 байтів
  тільки для ліній затримки. Додати їх до поточного вільного RAM неможливо.
  Потрібні звільнення ресурсів, компактні алгоритми й явні часові межі.
- Розмір RAM-знімка Temporary Save визначити після вибору формату звуку,
  патерна та locks; не створювати шість повних копій усіх DSP-буферів.
  Reload відновлює музичний стан, а не машинний стан процесора.

## Порядок наступних змін

1. Виділити параметри шести машин і зменшити набір движків кінцевої збірки.
2. Реалізувати й перевірити машини окремо, потім їхню спільну гру.
3. Зберегти locks, додати Control All з маскою та RAM Save/Reload без
   зупинки transport; перевірити повернення параметрів під час гри.
4. Підключити два LFO, поетапно реалізувати незалежні FX з вимірами бюджету.
5. Переробити UI й SAVE, після браузерних перевірок перейти до апаратних тестів.

На Linux регресійний набір не має macOS-лічильника host-інструкцій;
перевірка статичних pi32v2 render-loop budgets працює окремо.
Відсутні також заводські пакети та DaisySP для необов'язкових reference-тестів.
Фізичний FM-1 у цьому хмарному середовищі не тестувався.
